# 二维 TNT、实体物理与流体调查

调查日期：2026-10-24。范围已由用户确认：所有新功能只在二维搭建与微时序中进行。本轮只调查，未修改产品运行逻辑、版本号或分发包。

本文记录调查轮的历史状态；后续实现、当前可用能力与边界见[二维 TNT 与流体实现](二维TNT与流体实现.md)。

## 调查结论

项目已有简化 TNT，但距离原版行为还缺少实体与流体交互、爆炸冲量、完整点燃入口、正确的含水抗性和部分更新顺序。继续只向现有 `explodeEntity` 增加特例，会让后续掉落物、落沙、弹射物和载具继续重复实现物理。

建议先统一二维世界查询、实体类型默认值、流体状态与流体计划刻，再补全 TNT 和通用爆炸计算。保留现有事件推进、暂停和中途保存能力；不接入三维投影运行。

## TNT 自身需要还原的行为

### 生成与点燃

- 普通点燃默认引信 **80gt**，爆炸强度 **4**，类型尺寸为 `0.98F × 0.98F`，位置按方块底面中心生成。
- 原版点燃构造函数会取世界随机角度，赋予大小约 0.02 的水平初速度，以及 `0.2F` 的向上速度。发射器和连锁点燃也不能统一设成水平零速度。
- 被爆炸点燃时，默认短引信是 **10–29gt**，来自 `nextInt(20)+10`。已经用原版方法验证；不能写成包含 30 的区间。
- 点燃入口至少需要核对放置即供电、邻居供电、发射器 TNT、发射器打火石、手持打火石/火焰弹、着火弹射物、相邻火焰，以及爆炸连锁。所有入口应调用同一个 TNT 工厂与点燃过程。
- TNT 本身不因泡水取消引信；原版 TNT 类型免疫火焰，`hurtServer` 返回 false。伤害免疫不意味着免疫水流或爆炸冲量。

### 每刻次序

原版 `PrimedTnt.tick()` 的关键顺序是：

1. 传送门处理。
2. 施加重力，默认每刻向下加速度 0.04。
3. 按速度移动、处理碰撞。
4. 应用经过或接触方块的效果。
5. 速度乘空气阻力 `0.98F`。
6. 若落地，再将 X/Z 速度乘 0.7，Y 速度乘 -0.5；实际 Y 速度还受前面的碰撞恢复影响，不能直接套一个“每次落地弹起”的公式。
7. 引信减一；到期先移除源实体，再执行爆炸。
8. 未到期才更新流体交互，因此本次水流冲量通常影响下一次移动。

碰撞恢复还应核对黏液块等有弹性的地面；原版 26.3 的 `Entity.restituteMovementAfterCollisions` 已包含弹性与重力补偿，不能用统一归零规则覆盖全部情况。TNT 不调用普通生物的整套 AI 或移动逻辑，也不能靠给其他实体套用 TNT 的运动参数实现通用物理。

### 爆心与显示

- 爆心是 `(x, y + 实体高度×0.0625, z)`，不是实体脚底，也不是几何中心。默认高度时偏移约 **0.0612500012**，会影响台阶、灵魂沙、水边界和遮挡结果。
- 普通 TNT 爆炸参数 `fire=false`，不应额外生成一圈火。
- 最后 10gt 的膨胀和每 5gt 交替的白色闪烁可以沿用原版显示公式，但显示不能消耗模拟随机数，也不能改变引信推进。

## 流体需要建立的公共能力

### 一份流体状态

运行中的世界需要提供 `getFluidState(pos)`：同时识别水方块、流动水、含水方块和气泡柱中的水。流体不能只存在于画布的 `water` 绘制缓存中，也不能只用“实体脚下是不是 water”判断。

原版普通水源的自身高度是 `8/9`，上方连着同类水时查询高度为 1。流动水还区分数量与 `FALLING`；方块的 `level=0..15` 和 `FluidState` 的 amount/falling 必须明确转换。不能把所有 water 都当一格高的水源。

### 流向与实体受力

- `FlowingFluid.getFlow` 根据四个水平邻居的流体高度差、邻居下方流体和阻流条件计算方向。
- 下落水邻接实心侧面时，还会加入向下分量；不能只推 X/Z。
- 实体以收缩 0.001 的 AABB 扫描触及的流体格，累计浸水高度和流向；不是采一个中心格。
- `Entity.updateFluidInteraction` 对水施加的基础速度增量系数为 **0.014**。熔岩为另一套尺度，不能和水共用一个阻力参数。
- **26.3 的非玩家实体会把汇总流向归一化后施加冲量，玩家则使用格数平均。** 低浸水深度先参与各格流向汇总，累计量过小会被跳过。需要按本版 `EntityFluidInteraction` 的实际顺序移植，不能照搬旧版本的平均公式。
- 原版公共累加器还有低速最小冲量条件；应原样验证其触发条件，不能给所有 TNT 每刻强加一个任意最小速度。
- 水流推力与实体自身浮力是两件事。TNT 仍受自身重力；掉落物则有专门的水中运动和向上微加速。船、生物、矿车也各有差异。
- 气泡柱属于方块接触效果。它区分柱内、柱顶、上升和下沉，后续可通过公共接触回调接入，而不是写进 TNT 专属方法。

### 流体计划刻

原版普通水流计划刻间隔为 **5gt**。`ServerLevel` 先执行方块计划刻，再执行流体计划刻，随后才进入后面的实体更新流程。建议在现有 TT 范围内增加明确的“方块计划刻 → 流体计划刻”子阶段，不把水流塞到 EU 末尾，也不使用画面刷新次数推进。

需要涵盖向下优先、坡度寻路、回落水位、水源转换规则、含水容器、墙面通水形状和冲刷/水岩浆交互。完整流体可以分步实现，但只有静态水位采样时，不能将其标为“原版水流扩散已完成”。

## 爆炸需要分开的计算

### 方块破坏

原版沿 `16×16×16` 立方体外壳采样，共 **1352 条射线**。每条有随机初始能量，按约 0.3 格前进，同时扣除空气衰减和所在格抗性。

关键差异包括：

- 有效抗性取 **方块抗性与该格流体抗性的最大值**。水/熔岩的抗性为 100；含水台阶不能仍按木台阶抗性 3 处理。
- 射线衰减读取整格 `FluidState`；实体浸水与水流推力则判断流体表面高度。两者不能用同一个“是否在水中”的布尔开关替代。
- 方向构造、初始能量与逐步能量衰减使用了 Java float 运算；当前全用 JavaScript double 和 `0.225`，不保证逐格一致。需要在关键运算处复现 float 精度。
- 先确定受影响集合，再计算实体影响，然后打乱方块顺序并逐个调用爆炸回调。不能把“先删掉所有方块，再算实体受力”作为实现顺序。
- 原版集合可包含空气位置；这些位置和集合迭代、打乱顺序会影响随机数消费。JS Set 的插入顺序不能直接当成原版 HashSet 的顺序。
- 方块掉落、容器内容物、移除更新和 `wasExploded` 不是简单的 `set(null)`；连锁 TNT 也不应像普通方块一样额外掉落 TNT 物品。

### 实体暴露度、伤害与冲量

强度 4 的 TNT 对实体的计算范围使用半径参数的两倍，即 8 格，不能沿用方块破坏射线的触及格数作为实体范围。

原版对目标 AABB 的多个采样点做碰撞射线检测，得到暴露度。这里使用 `COLLIDER` 且 **忽略流体遮挡**。水通常可以抑制方块破坏，但不能据此直接取消实体伤害和冲量；实心墙、半砖和活塞移动形状需要按实际碰撞形状遮挡。

令 `R=2×爆炸强度`、`d=目标位置与爆心距离`、`E=暴露度`，基础影响比例为 `p=(1-d/R)×E`。基础伤害为 `((p²+p)/2)×7R+1`，冲量还需结合方向、击退倍率和目标抗性。目标是已点燃 TNT 时，用脚底位置确定冲量方向；其他实体使用眼睛位置。伤害计算用目标位置衡量距离，不能把两种取点混为一谈。

通用接口应允许各实体分别处理伤害、冲量和爆炸命中回调。TNT 虽然不受该普通伤害，仍应接受冲量；这正是 TNT 炮及多颗 TNT 相互加速的基础。生物生命值、护甲、伤害冷却等需要另立范围，不能在尚未接入时声称已完成所有实体伤害。

### TNT 矿车

当前已有 TNT 矿车，需要单独验收，而不是直接使用普通 TNT 的所有规则：

- 激活轨点燃、碰撞速度阈值、坠落距离、着火箭与受损引爆入口不同。
- 爆炸强度还受速度、独立实体随机数和 `explosion_speed_factor` 影响。
- 点燃后的矿车对铁轨及其下方支撑方块有特殊的抗性和破坏判断。
- 引信减到零与真正爆炸的分支次序也应分别测试。

## 二维边界必须先固定

二维显示并不要求把实体内部位置和速度压缩成两个数字；保留现有三分量便于复用原版公式，也不意味着引入三维投影模拟。

目前侧视只保存 `z=0` 的方块，并把移动的 Z 分量置零；俯视只保存 `y=0` 方块，但实体仍可改变高度，另有一块隐式碰撞地面。当前爆炸查询不到这块地面，旧流体模型又另有二维边界语义。

建议在正式开发的第一步明确并形成夹具：

1. 侧视的面外空间按空气、封闭边界还是截面延伸处理；流体能否向面外流出，爆炸射线能否绕出截面。
2. 俯视保留实体高度和重力，以容纳 TNT 的初始跃起；隐式地面要统一参与流体阻挡、碰撞与爆炸遮挡，且不能生成可破坏、可掉落的隐藏方块。
3. 给侧视 TNT 的随机初速度、流体力和爆炸冲量施加同一种法向约束。不能只在移动时清零，而让隐藏速度一直累积。
4. 维护当前 192 格编辑边界、256 格实体清理边界与面外写入规则的明确关系。

不能同时承诺“任意原版三维装置的完全相同结果”和“严格单层二维世界”。推荐验收口径是：**二维边界规则明确；内部通用物理按 26.3；在匹配边界的原版夹具中逐刻对照。** 具体截面语义是下一轮设计需要确认的决定，本轮未修改现有行为。

## 建议接入结构与顺序

模块名是开发建议，不是本轮已经新增的运行模块。优先拆出已有长函数中的独立职责，保留当前矿车、库存和活塞接口。

| 2：流体公共层 | 候选 `board-fluids.js`：状态、高度、流向、计划刻、AABB 浸水与冲量 | 水可按 gt 扩散并推动实体；含水状态与画面一致 |
| 3：TNT 与通用爆炸 | 候选 `board-tnt.js`、`board-explosions.js`：点燃、运动、引信、抗性、暴露度、冲量、连锁与掉落回调 | 干地、水中、遮挡、多 TNT、矿车场景逐刻对照 |
| 4：界面和持久化 | TNT 操作入口、引信与速度查看、闪烁/爆炸效果、微时序记录、旧存档迁移 | 暂停/单步/撤销/存取后得到相同后续状态 |

供未来实体复用的能力应包括：类型默认值、空间查询、碰撞、流体采样、接触效果、通用冲量、伤害回调、生成/移除次序和序列化。掉落物浮力、船、矿车、落沙、弹射物和生物 AI 保留各自策略，不用一个大分支统一参数。

本轮不建议承诺同步实现生物 AI、完整战利品表、跨维度传送门、所有燃烧机制或三维联动。普通 TNT 的公共爆炸接口应留好扩展点，但这些工作有各自验收范围。

## 随机性、保存与性能

- 现有 `deviceNext` 已实现 48 位 Legacy LCG 并保存在快照，是可复用基础。但世界随机数、各实体随机数和 UI 随机数的归属仍需区分；不能用 `Math.random()` 替代物理随机源，也不能为了优化随意少取一次随机数。
- 需要保存流体计划刻、实体新增/移除游标、爆炸任务游标、未完成的方块破坏队列、所有物理随机源状态。原版实体迭代采用写时复制，迭代中新增实体不进入原来的本刻迭代；现有 EU 快照队列可沿此方向扩展。
- 现有 100000 事件预算不会自动覆盖爆炸射线函数内部的同步循环。大量 TNT 的射线、暴露度和方块更新需要可暂停的工作预算；暂停后续算不能重取随机数或重做已完成的破坏。
- 可预计算 1352 条静态射线方向，使用局部方块查询缓存、实体空间索引和精确碰撞形状缓存。不能缓存跨越方块变化的暴露度；第一颗 TNT 炸掉墙后，第二颗必须使用新世界状态。
- UI 每帧目前最多推进一个 gt，低帧率时实际运行会变慢。引信仍应以模拟 gt 为准；是否使用可控追帧或 Worker 是后续性能选择，不应改成独立墙钟计时器让暂停的 TNT 继续倒计时。
